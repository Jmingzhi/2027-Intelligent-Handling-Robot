# 决策记录（ADR）

> **ADR = Architecture Decision Record（架构决策记录）**
>
> ## 为什么三人队必须有这个
> 三人队最容易犯的错误不是技术难，而是**同一个问题反复讨论、反复推翻**。
> 每次讨论"用 ROS 还是裸机""用折叠臂还是固定臂""要不要双相机"，
> 两周后没人记得当初为什么这么定，于是重新吵一遍。
>
> **决策一旦做出就写在这里，之后不再重复讨论。**

---

## 1. 什么情况需要写 ADR

| 需要写 ✅ | 不需要写 ❌ |
|---|---|
| 涉及**多人**的决策 | 个人实现细节 |
| 影响**接口**的决策 | 可随时改的局部选择 |
| **难以回退**的决策（涉及加工件、架构） | 改个参数就能变的 |
| 有**多个合理备选**的决策 | 明显只有一种做法 |
| 会影响**进度/成本**的决策 | — |
| 涉及**合规**的决策（买什么、能不能买） | — |

**经验判据**：如果你觉得"这个决定以后可能会有人问为什么"，就写 ADR。

---

## 2. 编号与命名

```
docs/50-决策记录/ADR-0001-简短标题.md
```

| 规则 | 说明 |
|---|---|
| 编号 | 4 位数字，从 `0001` 起，**只增不改** |
| 标题 | 简短、能看出决策内容，不写"关于XXX的决定" |
| 一个 ADR | **只记录一个决策**（多个决策拆开写） |
| 已接受的 ADR | **不修改内容**，需要变更时新写一个并标注"取代 ADR-XXXX" |

**命名示例**

```
ADR-0001-采用折叠臂构型.md
ADR-0002-不引入ROS采用裸机方案.md
ADR-0003-采用单相机方案.md
ADR-0004-落点精度采用末端二次精定位.md
```

---

## 3. 状态定义

| 状态 | 含义 |
|---|---|
| **提议** | 正在讨论，未定 |
| **已接受** | 已决定并生效 |
| **已废弃** | 曾经有效，现已不适用 |
| **被取代** | 已被新的 ADR 取代（要写明被哪个取代） |

---

## 4. 流程

```
① 发现需要决策的问题
      ↓
② 开 Issue（用 decision.yml 模板）说明背景与备选方案
      ↓
③ 三人讨论 → 拍板
      ↓
④ 写 ADR（用 ADR模板.md）→ 提交到本目录
      ↓
⑤ 在 Issue 里回填决议与 ADR 链接
      ↓
⑥ 以后不再重复讨论这个问题
```

**决策权归属**

| 决策范围 | 谁拍板 |
|---|---|
| 系统级 / 跨模块 / 接口 | A（系统集成） |
| 机械与结构 | B |
| 电控、视觉、算法 | C |
| 争议无法解决 | A 有最终决定权，但须记录分歧 |

## 7. 复审机制

| 情形 | 处理 |
|---|---|
| 决策做出了但发现不可行 | 新写 ADR 标注"取代 ADR-XXXX"，说明原因 |
| 阶段评审时 | 逐个核对已接受的 ADR 是否仍然成立 |
| 硬件/规则发生重大变化 | 主动复审相关 ADR |

> ⚠️ **不要直接修改已接受的 ADR**。历史决策的价值在于"记录当时的判断依据"，
> 改了就看不出认知是如何演进的，也无法复盘。
