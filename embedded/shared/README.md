# 通信协议共享定义

> ## 为什么这个目录存在
>
> 通信协议会被**至少三方**使用：
> 1. **固件**（C/C++）—— 收发协议帧
> 2. **视觉 / 上位机 / tools**（Python）—— 收发协议帧
> 3. **测试与调试脚本** —— 解析协议帧
>
> **如果三方各自复制粘贴一份协议定义，必然出现不一致。**
> 表现是"帧能收到但校验总失败"、"命令码对不上导致动作错乱"。
> 排查这类问题极其耗时。
>
> **因此：协议定义只能有一份真源，就在这里。**

---

## 文件规划

| 文件 | 语言 | 用途 |
|---|---|---|
| `protocol.h` | C | 帧格式、命令码、错误码、结构体定义 |
| `protocol.c` | C | 打包、解包、CRC 计算 |
| `protocol.py` | Python | Python 侧等价实现（视觉 / 上位机 / tools） |
| `test_protocol.py` | Python | 单元测试，**含 CRC 黄金测试向量** |

> ⚠️ 硬件未定，这些文件尚未创建（见 [../../docs/60-项目管理/待确认清单.md](../../docs/60-项目管理/待确认清单.md)）。

## 唯一真源原则

| 做法 | 是否允许 |
|---|---|
| 固件 `#include "shared/protocol.h"` | ✅ 正确 |
| Python `from shared.protocol import ...` | ✅ 正确 |
| 把 `protocol.h` 里的命令码抄到另一个文件 | ❌ **禁止** |
| 在 Python 里"照着手册重新写一遍"命令码 | ❌ **禁止** |

**若因语言限制无法直接引用**，则：

1. 用**代码生成**（从一份定义生成 .h 和 .py）
2. 或维护一份**共享常量表**（如 `commands.json`），两边都从它加载
3. 并在 CI 中校验两边一致

## ★ CRC 黄金测试向量（交叉验证手段）

CRC 实现最容易"看起来对但其实不对"。**用标准测试向量交叉验证两边的实现。**

| 项 | 值 |
|---|---|
| 算法 | **CRC-16/CCITT-FALSE** |
| 多项式 | `0x1021` |
| 初值 | `0xFFFF` |
| 输入反射 | 否 |
| 输出异或 | 否 |
| **黄金测试向量** | 输入字符串 `"123456789"`（9 字节 ASCII） |
| **期望结果** | **`0x29B1`** |

```
输入: 31 32 33 34 35 36 37 38 39   ("123456789")
期望: 0x29B1
```

> ⚠️ **C 实现与 Python 实现的结果都必须等于 `0x29B1`。**
> 如果两边都等于这个值，说明实现一致；如果不等，先修好再往下做。
>
> **这个测试必须写进 `test_protocol.py` 并纳入 CI。**

---

## 参考实现（C）

```c
/* CRC-16/CCITT-FALSE: poly=0x1021, init=0xFFFF, no reflect, no xorout */
uint16_t crc16_ccitt(const uint8_t *data, uint16_t len)
{
    uint16_t crc = 0xFFFF;
    for (uint16_t i = 0; i < len; i++) {
        crc ^= (uint16_t)data[i] << 8;
        for (uint8_t b = 0; b < 8; b++) {
            crc = (crc & 0x8000) ? (uint16_t)((crc << 1) ^ 0x1021)
                                 : (uint16_t)(crc << 1);
        }
    }
    return crc;
}
```

## 跨模块的关键约束

> ⚠️ 规则：「**物料没有放置到搬运机器人上不能向下一个区域运行**」。
> 因此 `STOW_STATUS`（料仓在位状态）是**硬需求**的支撑，必须可靠实现。

> ⚠️ 规则：「**不允许任何方式遥控**」。
> 因此**调试通道（笔记本）只能读日志、写参数，不能控制动作**。
> 建议在协议层面就不给调试地址下发运动命令的权限，并写入代码评审检查项。

## 修改协议的正确流程

```
① 先改文档：docs/10-接口契约/通信协议.md
        ▼
② 同步改 protocol.h 与 protocol.py（★ 同一次提交）
        ▼
③ 更新 test_protocol.py 的测试向量（如有变化）
        ▼
④ 本地跑测试：CRC 黄金向量必须仍为 0x29B1
        ▼
⑤ 通知对端（固件 ↔ 视觉）双方确认
        ▼
⑥ 在 PR 描述中声明"影响接口"，并勾选"共享代码一致性检查"
   （见 docs/90-模板/PR描述模板.md 4.3 节）
        ▼
⑦ CI 通过后合并
```

### 五条纪律

| # | 纪律 | 理由 |
|---|---|---|
| 1 | **文档先行** | 文档是权威定义，代码是它的实现 |
| 2 | **一次提交改两边** | 分开提交会产生"中间不一致"的窗口 |
| 3 | **绝不复制粘贴到其他目录** | 复制 = 产生了第二份真源 |
| 4 | **改协议必须通知对端** | 三人队没有"自动通知"，必须显式做 |
| 5 | **黄金向量必须保持通过** | 它是最后一道防线 |

### 明确禁止的事项

| # | 禁止 | 后果 |
|---|---|---|
| 1 | 在 `vision/src/` 里自己写一份帧解析 | 出现第二份真源 |
| 2 | 在 `tools/` 里复制一套命令码 | 同上 |
| 3 | 只改一边然后"回头再改另一边" | 现场故障 |
| 4 | 改了协议不更新测试向量 | 测试失去保护意义 |
| 5 | 用注释掉的方式"临时"改常量 | 极易被误提交 |

## 单元测试要求

`test_protocol.py` 必须覆盖以下内容，并纳入 CI（`.github/workflows/ci-python.yml`）。

| # | 测试项 | 判据 | 优先级 |
|---|---|---|---|
| 1 | ★ **CRC 黄金向量** | `"123456789"` → **`0x29B1`** | 🔴 必须 |
| 2 | CRC 空输入 | 与 C 侧独立算出的结果一致 | 🔴 |
| 3 | CRC 单字节 | 与 C 侧一致 | 🟡 |
| 4 | **帧往返**：`pack` → `parse` 得到相同内容 | 往返一致 | 🔴 |
| 5 | 帧总长度 | `LEN + 8` | 🔴 |
| 6 | `HEAD` / `TAIL` 校验 | 错误头尾被拒绝 | 🔴 |
| 7 | CRC 错误的帧被拒绝 | 返回相应错误码 | 🔴 |
| 8 | 超长 `PAYLOAD`（>255）被拒绝 | 拒绝 | 🟡 |
| 9 | 截断的帧被正确处理 | 不崩溃、不误解析 | 🔴 |
| 10 | 粘包 / 分包处理 | 能正确切分 | 🔴 |
| 11 | ★ **命令码集合与 `protocol.h` 一致** | CI 自动比对 | 🔴 |
| 12 | 字节序验证 | 小端 | 🔴 |
| 13 | 各命令的 `PAYLOAD` 编解码 | 字段值正确 | 🟡 |
| 14 | 错误码取值一致性 | 与 `protocol.h` 一致 | 🟡 |

> ⚠️ **第 11 项是"防复制粘贴"的自动化手段**：
> CI 用脚本解析 `protocol.h` 里的命令码，与 `protocol.py` 中的比较，
> 不一致则构建失败。**这是唯一能长期防住"两边改不同步"的机制。**

### 与 C 侧的交叉验证

| 场景 | 做法 |
|---|---|
| C 侧无法直接跑单元测试（嵌入式目标） | ★ **在 PC 上编译 `protocol.c` + 测试桩**，跑同样的向量 |
| 只做一次性验证 | ⚠️ 不够——每次改协议都要重跑 |
| 建议 | 在 CI 中增加"C 侧向量测试"任务（用宿主编译器编译 `protocol.c`） |

> 💡 **"在 PC 上编译固件的协议层来测"** 是嵌入式项目的标准做法，
> 成本很低、收益很高，能把 CRC 这类问题挡在代码评审阶段。
